# OpenPoker 实盘每批（约 500 手）分析框架

适用：OpenPoker / wopo 实盘，每打完约 500 手做一次复盘。
数据来源：一个 run 目录下的 `openpoker_ws.jsonl`（服务器原始消息）、`openpoker_actions.jsonl`（每次决策的请求 / 回复 / 发出的动作）、
`openpoker_hh.jsonl`（手牌记录）、`play.log`。
参照样例：`docs/temp/openpoker_9max_live_run5_analysis_2026_10_17.md`（run5，805 手）。

标注约定沿用 run5：**[事实]** = 数据里直接数出来或逐条核对过；**[推断]** = 有数据支撑但没直接验证；**[推测]** = 只是可能的解释。

## 0. 基本原则：500 手看不出赢率

按 run5，每手标准差约 18.5 BB。500 手的 bb/100 标准误约 83，95% 区间约 ±160 bb/100——打出 +100 和 −100 都可能只是运气。
要把 ±10 bb/100 的差别分到 95% 置信，大约需要 13 万手。

所以每批 500 手主要回答两个问题：

1. **程序有没有按设计在跑**（数据、工程、决策路径、打法统计）——这些不依赖输赢，500 手足够看清。
2. **有没有明显打错的牌**（关键手复盘）——这才是"打得好不好"的主要依据。

赢率只在多批累计之后看。下面分六层，**前一层不过关，后面的层就不用看**。

## 1. 第 0 层：数据能不能信（不过关就停）

| 检查项 | 怎么算 | 标准 |
|---|---|---|
| 净输赢口径 | 用 ws 消息逐手串链：每次 `table_joined` 开一段，段内每手净输赢 = 本手 `final_stacks[我方座]` − 上一手（段内第一手减起点栈）。**不用 hh 的 `stacks_start`** | 固定用这个口径 |
| 零和 | 每手所有座位开局栈（首个翻前 table_state 的 stack + bet）之和 = `final_stacks` 之和 | 100% |
| 串链连续 | 串链得到的开局栈 = 服务器 table_state 给的开局栈 | 100% |
| 请求栈一致 | 每次决策请求的 `stacks` / `dealt_seats`，和服务器 table_state 逐座比对 | 100% |
| 缺结果的手 | 发了牌但没有 `hand_result` 的手 | 逐手列出原因 |
| hh 自身错误 | hh 和 ws 串链对不上的手（run5 有 4 类） | 列出并归类 |

任何一项对不上，这一批的输赢数字就不能用，先查 driver。

## 2. 第 1 层：工程稳不稳

这一层的损失是确定的，跟运气无关，优先级最高。

| 指标 | 参考（run5 / 修复后的期望） |
|---|---|
| 每小时手数、相邻两手间隔的中位数 | run5：93.5 手/小时，间隔中位数 33 秒 |
| 意外断线次数、每次断了多久、断线期间服务器替我方弃了几手 | 修复后每 500 手应 ≤ 1–2 次 |
| 整桌卡死、以 `table_closed` 收场的次数 | 0 |
| 离桌 / 进大厅次数，以及它和入座次数之比 | 不应再出现几千轮的循环（run5 修复前 3163 轮） |
| 动作被拒、被限速丢弃、超时自动弃牌 | 0 |
| 决策耗时 p50 / p99 / 最大值（按街） | p99 在服务器时限以内留出余量 |
| advisor 内存峰值、子树节点数峰值、超出节点上限的次数 | 不贴着上限跑 |
| 入座原因分布：码深漂移离场 / 输光 / 关桌转桌 | 和上一批对比，突然变化要查 |

## 3. 第 2 层：决策路径健不健康

按街统计每次决策的 `resp.source`：`blueprint` / `search` / `search:unanchored` / `limp_heuristic` / `fallback:*` / `search_giveup:*`。

| 检查项 | 标准 |
|---|---|
| 兜底率（`fallback:*` + `search_giveup:*`）/ 总决策数 | run5 是 2.3%（其中 18 次是翻前全下启发式）；比上一批明显升高就逐个查原因 |
| 按均匀分布出牌（blueprint 或搜索） | **必须是 0**，出现一次就是 bug |
| `search:bp_placeholder` | 0 |
| 翻牌阶段 blueprint 占比；尺寸门、码深门各挡下多少次 | 代码不变时应稳定；变化大说明桌况（人数、码深）变了或有回归 |
| 抽样是否诚实 | 同一类决策点上，`probs` 的期望频率对比实际选中的频率（例：所有翻前点 raise 概率之和 vs 实际 raise 次数）；偏差超过 2–3 个标准误就要查 |
| 低于 5% 的全下被选中 | 0（advisor 抽样前会去掉概率低于 5% 的全下，选中即 bug） |
| 其他低概率动作（< 5% 的非全下动作）被选中 | 不算 bug，但列出来，进入第 4 层的复盘候选 |

各来源所在手的净输赢可以列出来，但会被几手大底池左右，**不能拿来比较来源好坏**。

## 4. 第 3 层：打法统计有没有跑偏

比例类统计在 500 手时已经比较稳，例如 VPIP 在 21% 附近时的标准误约 1.8%。

| 统计 | 拆分方式 |
|---|---|
| VPIP / PFR / 3bet / 面对 3bet 弃牌率 | 位置 × 实际桌上人数（6 / 5 / 4 人分开） |
| 翻牌持续下注率、面对持续下注弃牌率 | 单挑底池 / 多人底池 |
| 摊牌率（WTSD）、摊牌胜率（W$SD） | 总体 |
| 翻后全下次数，以及全下时的胜率分布 | 按街、按底池人数 |
| 平跟池（limp）占比、平跟池里我方的结果 | — |

**主要比较对象是策略自己**：期望值直接从 actions 日志的 `probs` 算（例如每个翻前点非弃牌概率的平均值，就是"策略应有的 VPIP"）。
实际值和期望值差得多，说明抽样、来源切换或启发式有问题。
和人类常规玩家的数字比（6 人桌 VPIP 大约 22–28%）只用来粗查方向，蓝图本来就可能和人的打法不一样。

**重点盯一项：翻后全下时胜率 < 30% 的次数和占比。** run5 里翻后 20 次全下有 11 次是弱牌，合计约 −526 BB，5 次输光全在这里。
修了之后要逐批看这项有没有降下来。

## 5. 第 4 层：关键手复盘（真正回答"打得好不好"）

统计只能指出哪里可疑，打得好不好要落到具体的牌上判断。每批固定挑这几类：

1. 所有输光的手
2. 输得最多的 10 手、赢得最多的 5 手（赢的也要看，是不是靠对手送）
3. 翻后弱牌全下（全下时胜率 < 30%）
4. 强牌弃牌（例如翻后弃掉两对以上，或弃牌时胜率明显高于底池赔率）
5. 所有兜底 / 放弃搜索的点
6. 选中了低概率（< 5%）动作的点

每手只归到一类：

| 类别 | 含义 | 下一步 |
|---|---|---|
| **A 合理-运气** | 决策合理，全下那一刻胜率没问题，输了也正常 | 无 |
| **B 策略可疑** | 解本身给出了奇怪的动作 | 离线重放该点：换随机种子、迭代次数、`range_mix` 各跑几组。结果不稳 → 搜索没收敛；稳但仍奇怪 → 抽象或范围估计的问题 |
| **C 程序 bug** | 状态错位、重放非法、走错来源 | 用该手的请求写单测 |
| **D 启发式失误** | limp_heuristic、翻前全下启发式等手写规则判断错 | 积累样本后再调规则，单例不改 |

B / C / D 进问题清单，标严重程度，下一批验证是否修好。
**判断这一批打得好不好，主要看 B + C + D 有多少手、涉及多少 BB，而不是看净输赢。**

## 6. 第 5 层：战绩（放最后，只看累计）

| 项 | 说明 |
|---|---|
| 原始 bb/100 | 附标准误和 95% 区间 |
| 全下折算 bb/100 | 两人摊牌、钱在河牌前全进去的手，按全下那一刻的胜率折算；只修正这部分运气 |
| AIVAT bb/100 | `tools/openpoker_hh_aivat.rs` 已能读 hh，降方差比全下折算更多。用之前先确认 hh 的已知错误修好了，或改为从 ws 生成输入 |
| 大底池集中度 | 绝对值 ≥ 50 BB 的手合计多少，其余手合计多少 |
| 按位置的净输赢 | 只看方向（盲注位输、后位赢算正常），数值本身不用 |

### 跨批累计表

每批加一行，赢率只在这张表上下结论：

| 批次 | 代码版本 | 手数 | 原始 bb/100 | 折算 bb/100 | AIVAT bb/100 | 累计手数 | 累计 AIVAT ± 标准误 | 兜底率 | 弱牌全下次数 | 断线次数 |
|---|---|---|---|---|---|---|---|---|---|---|

代码改动会让批次之间不可比：

- 只影响工程层的改动（重连、日志），可以继续累加。
- 动了策略的改动（剪枝、尺寸门、启发式、搜索参数），从这一批起重新开一段累计。

## 7. 每批报告的固定格式

文件放 `docs/temp/openpoker_<桌型>_live_<run名>_analysis_<日期>.md`，结构：

1. **要点**（5 行以内）：数据是否可信、工程问题、新发现的 B / C 类问题、上一批问题是否修好、累计战绩一句话。
2. **第 0–3 层**：每项标"正常 / 关注 / 异常"，附和上一批的对比。
3. **第 4 层**：逐手列出 hand_id、分类、依据、下一步。
4. **问题清单**：按严重程度排序，沿用上一批的编号，延续未解决的条目。
5. **累计表**：追加本批一行。

## 8. 自动化

第 0–3 层的全部数字、第 4 层的候选手列表，都可以由脚本从 run 目录直接算出（输入 run 目录，输出上面各表）。
第 4 层的分类和离线重放需要人看。
